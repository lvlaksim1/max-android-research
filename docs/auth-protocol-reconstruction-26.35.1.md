# Авторизация MAX Android 26.35.1 — восстановленные элементы протокола

Дата анализа: 25 октября 2026 года. Образец: `ru.oneme.app`, версия 26.35.1 (6867).
Контрольная сумма APK: `e809176d6bf6ff69247274433ec170a5db8a5687a02a04299a78a2ae978119fc`.

**Метод:** проверка исходного APK, декомпиляция 24 272 файлов Java посредством JADX в GitHub Actions, поиск вызывающих классов, конструкторов команд и обработчиков ответов. Код обфусцирован; некоторые сложные методы JADX восстанавливает с ошибками. **Живой сетевой обмен и успешная авторизация пока не записаны.**

## 1. Начало входа по номеру

1. Экран `one/me/login/inputphone/InputPhoneScreen.java` связывает кнопку «Продолжить» с `defpackage/ty3.java`.
2. `ty3.onClick()` запускает выполнение `defpackage/yr0.java` через модель `u79`.
3. `yr0.B()` объединяет код страны и введённый номер, удаляет лишние символы через `b79.i`, проверяет наличие номера в уже подключённых аккаунтах посредством `d2c.g(...)` и вызывает `ej0.a(номер, 1, ...)`.
4. `ej0.a()` организует исполнение `cj0` с повтором при `session.sequence`, определённым в `dj0`.
5. `cj0` собирает запрос `new aj0(режим, последовательность_сеанса, номер, mode)` и отправляет его через `ctc` / `f7j`.

## 2. Конструктор исходящего запроса

Прямое доказательство — `defpackage/aj0.java` (файл приведён в `evidence/auth-code-matches-26.35.1.md`).

| Элемент | Доказанный смысл на уровне программного объекта |
|---|---|
| `tdd.l` | `AUTH_REQUEST`, в каталоге команд указано значение 17 |
| `phone` | Нормализованный номер в виде строки |
| `type` | `START_AUTH` при режиме 1, `RESEND` при режиме 2 |
| `mode` | Необязательная последовательность байтов |
| `p()` | Возвращает значение последовательности текущего сеанса, полученное при создании команды |

**Это описание полей объекта команды, не пример сетевого JSON-запроса.** Точное двоичное кодирование, транспортные заголовки и сервер для конкретного сеанса ещё не подтверждены.

`cj0` получает значение последовательности из `bcc.l` (иначе `-1`). Необязательное `mode` создаётся методом `v99.a(...)`: сначала проверяется подготовленный массив байтов; при его отсутствии и наличии идентификатора сеанса вызывается `CallsSdkInitializer.initializeSessionSeed(...)`. Назначение алгоритма и формат полученных байтов не определены.

`dj0` допускает повтор при исключении `TamErrorException` с идентификатором `session.sequence` и счётчиком повтора `< 3`. Это узкая ветвь обработки ошибки, а не универсальное правило повторов всех запросов.

## 3. Разбор ответа сервера

Декомпилированный разборщик `defpackage/bj0.java` распознаёт следующие ключи:

| Поле | Статический вывод |
|---|---|
| `token` | Строковое значение ответа, передаваемое на экран как проверочный токен |
| `codeLength` | Ожидаемая длина кода |
| `requestCountLeft` | Оставшееся число запросов, указанное сервером |
| `requestMaxDuration` | Временной параметр запроса |
| `altActionDuration` | Временной параметр альтернативного действия |
| `callOutParams` | Вложенный блок параметров подтверждения звонком |
| `callOutParams.trackId` | Идентификатор процесса проверки звонком |
| `callOutParams.ttl` | Срок действия, передаваемый в обработку звонка |
| `callOutParams.pollingInterval` | Интервал опроса результата звонка |

Точные единицы измерения всех полей времени и семантика предельных значений требуют отдельной проверки.

Переход к обычному коду реализован через `h79` → `ka9.d(...)` → `ConfirmPhoneScreen`. Экран принимает `verify_token`, `phone`, `code_length`, `code_resend`, `country_name_code`.

Альтернативная ветвь `ka9.e(...)` открывает `ConfirmPhoneCallOutScreen`. Экран хранит `phone`, `track_id`, `time_out`, `call_number`, `polling_interval`. Его модель `lp4` содержит задачу опроса `pollingJob`; видны варианты результатов `NumberAssigned`, `VerificationPassed`, `VerificationTimeout`.

**Осторожно:** в восстановленном методе `yr0.B()` есть противоречивые условия ветвления возле `callOutParams` (в одной ветви объект проверяется на `null`, после чего он разыменовывается в соседней ветви). Поэтому условие выбора метода подтверждения не следует считать точно восстановленным по тексту JADX.

## 4. Сетевой слой и прочие команды

В каталоге `defpackage/tdd.java` обнаружены следующие команды:

| Имя | Значение каталога |
|---|---:|
| `AUTH_REQUEST` | 17 |
| `AUTH` | 18 |
| `LOGIN` | 19 |
| `AUTH_CONFIRM` | 23 |
| `AUTH_CREATE_TRACK` | 112 |
| `AUTH_BY_TRACK` | 291 |
| `AUTH_CHECK_CALL` | 294 |

Значения обнаружены в классе команд. Для доказательства точного расположения поля команды в пакете требуется исследование сериализатора.

Строка `api/v3/ws` встречается в `p0b.b()`, где выполняется **подключение к серверу уведомлений** с параметром `push_tokens`; это **не доказанная точка авторизации**.

## 5. Достоверность и непроверенные элементы

**Установлено статически:** реальный конструктор команды запроса входа, его поля и варианты `START_AUTH` / `RESEND`, привязка к механизму сеанса, обработка отдельных ошибок, ключи ответа и переходы к экранам кода и звонка.

**Не установлено:** фактический адрес сервера авторизации, полный формат транспорта, сериализация команды `AUTH_CONFIRM`, поля для проверки SMS-кода, парольные ветви, получение учётных ключей, их сохранение и обновление, реальные сетевые заголовки, антизлоупотребительные проверки, успешное выполнение входа на сервере.
