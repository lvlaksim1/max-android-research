# MAX Android 26.35.1 — итог углублённого исследования авторизации

**Образец:** `base.apk`, версия 26.35.1 (6867), пакет `ru.oneme.app`, SHA-256 `e809176d6bf6ff69247274433ec170a5db8a5687a02a04299a78a2ae978119fc`.

**Методика:** контрольная сумма исходного APK; декомпиляция трёх DEX через JADX; просмотр вызывающих процедур, классов команд, десериализаторов ответов и механизма сеанса. Исследовано 24 272 декомпилированных Java-файла. Версия и хэш соответствуют зафиксированному образцу, но подлинность издателя отдельно не подтверждена.

**Граница верификации:** все перечисленные ниже сведения относятся к статическому анализу. Не проводилась настоящая авторизация тестовой учётной записи; сетевой пакет до и после TLS не записывался. Полный успешный вход и совместимость независимого клиента с рабочим сервером не доказаны.

## 2. Разбор ответа AUTH и данные пользователя

`th0` содержит словарь токенов, список значений, дополнительный набор атрибутов и объект профиля `cqe`. После выполнения `AUTH`, функция `ki0.a` проверяет наличие ключа `LOGIN` в словаре и вызывает `f0f.d(profile, loginToken)`.

`cqe` имеет три части: `ey4` (контактные данные профиля), `LinkedHashMap` ограничений и список параметров профиля. `f0f.d` также обрабатывает идентификатор пользователя и обновление структуры профиля.

Входной токен для `k7a` либо передаётся при создании задачи входа `i7a`, либо считывается через `dtc.c()` из локального состояния. Это указывает на возможность повторного входа после перезапуска или переподключения.

## 3. Другие способы подтверждения

При ответе с `callOutParams` обнаружены `trackId`, `ttl`, `pollingInterval`. Экран `ConfirmPhoneCallOutScreen` и модель `lp4` реализуют состояние проверки звонком и периодический опрос. Обнаружены состояния `NumberAssigned`, `VerificationPassed`, `VerificationTimeout`.

`AUTH_CONFIRM` (23), реализованная в `wh0`, формирует `tokenType=REGISTER` и поля `firstName`, опционально `lastName`, `photoId`, `avatarType`. Следовательно, называть эту команду обычной проверкой SMS неправильно.

В каталоге найдены также `AUTH_BY_TRACK`, `AUTH_CHECK_CALL`, `AUTH_CHECK_PASSWORD`, `AUTH_2FA`. Для этих ветвей наличие команды само по себе не доказывает полноту восстановленного обмена.

## 4. Сохранение токена и повторный вход

**Прямое доказательство, `u6.java`, ветвь 11, строки 126–137.** Метод, вызванный из `f0f.d(...)`, выполняет запись через `qi0.e(...)`:

| Ключ хранилища | Источник значения |
|---|---|
| `auth.account.name` | Имя профиля из `cqe.a.a()`, если оно не пустое |
| `auth.token` | Строковый токен `LOGIN`, полученный после проверки кода |

**Проверка чтения, `dtc.java`, строки 17–29 и 39–41.** Метод `dtc.c()` читает `auth.token` из настроек аккаунта и возвращает его лишь при наличии пользователя и непустом токене; метод `dtc.e()` записывает значение под этим ключом. `qi0` наследует общий механизм настроек `a4`. По этим фрагментам нельзя заключить, что данные шифруются на диске.

**Прямое доказательство, `c5h.java`, строки 69–109.** При обработке `SESSION_INIT` программа читает сохранённый токен из `dtc.c()`. Если он отсутствует, `LOGIN` не отправляется. Если присутствует, `c5h` вычисляет дополнительные параметры сеанса и создаёт `i7a`, из которой формируется `LOGIN`.

**Прямое доказательство, `c5h.n()`, строки 120–160.** Команда `SESSION_INIT` включает составной `userAgent`: тип устройства `ANDROID`, `appVersion=26.35.1`, `buildNumber=6867`, архитектуру, версию ОС, локаль, устройство, экран, часовой пояс и прочие параметры. В теле также присутствуют `deviceId`, `clientSessionId`, опционально `mt_instanceid`.

Это подтверждает механизм долговременного повторного входа по локально сохранённому токену. Но способ защиты значений в локальном хранилище, право на использование этого токена независимым клиентом и полная последовательность транспортного рукопожатия отдельно не доказаны.

## 5. Сеанс и транспорт

Клиентская команда наследуется от `u6j`: номер команды берётся из `tdd`, а поля помещаются в `i00`. Слой `r1g` отправляет команды через `z6j` и объект соединения `bcc`. Контроллер сеанса различает отключённое, подключённое и авторизованное состояния. Параметры `server.host`, `server.port` и `server.useTls` присутствуют в локальных настройках. **Код `o57.java`, строки 38–64, задаёт по умолчанию `api2.oneme.ru`, порт `443` и берёт признак TLS из `server.useTls` (по умолчанию включён).** В `o57.b()`, строки 111–170, клиент создаёт соединение с этим узлом и использует параметр ожидания `15000` миллисекунд; после истечения ожидания предусматривается сброс состояния DNS для узла.

`api/v3/ws`, найденный в `p0b`, относится к соединению уведомлений с `push_tokens`, а не к подтверждённой точке авторизации.

Точные сетевые пакеты, параметры транспортного рукопожатия, правила выбора рабочего узла и двоичное представление сериализованной команды без фактического сетевого захвата или дополнительного анализа соответствующего кодировщика не подтверждены.

## 6. Обработка ошибок

Для ошибки `session.sequence` в `dj0` существует ограниченный повтор (пока счётчик менее трёх). Эта логика специфична для определённого исключения и не означает универсальное правило повторов.

## 8. Что необходимо для окончательной проверки

Полностью завершить исследование именно **работающего серверного протокола** только по APK нельзя. Требуется собственный тестовый вход на устройстве с разрешённой записью сетевого обмена, чтобы сверить адрес, транспортное рукопожатие, последовательность команд, поля сессионных ключей, поведение при истечении срока действия и повторном запуске.

Такой тест в рамках данного исследования не выполнен. Наличие статически обнаруженных полей **не является доказательством** того, что независимый клиент может авторизоваться и работать с сервером.

Сохранение `auth.token` и порядок `SESSION_INIT` → `LOGIN` восстановлены по исходному коду. **Поиск по имени `refreshToken` недостаточен:** в APK имеются сторонние механизмы обновления токенов Firebase и звонков, которые не доказывают обновление собственно `auth.token` MAX. Необходимы отдельная проверка механизма обновления авторизации MAX и динамическое сопоставление сетевых кадров.
